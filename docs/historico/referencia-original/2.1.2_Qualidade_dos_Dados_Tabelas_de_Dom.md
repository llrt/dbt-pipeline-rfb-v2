# Análise da Qualidade de Dados das Bases Cruas


Na sequência, faremos uma breve análise da qualidade dos dados das bases cruas recém carregadas. Essa análise é importante para detectar (e se possível corrigir) possíveis problemas que possam afetar as análises futuras.

### [markdown]

Vamos começar primeiro pelas tabelas de domínio da Base dos Dados (Municípios e CNAEs). O esperado é que as tabelas estejam todas preenchidas, sem registros com campos vazios.


### [markdown]

### - Municípios / Base dos Dados (tabela municipio_bd)

### [markdown]
Os dados da tabela de `municipio_bd` são provenientes do portal Base dos Dados (BD) e tem descrições e metadados disponíveis em:

https://basedosdados.org/dataset/33b49786-fb5f-496f-bb7c-9811c985af8e?table=dffb65ac-9df9-4151-94bf-88c45bfcb056

Apesar de termos descritos os tipos (que são majoritariamente string/char), por simplificidade, inicialmente também deixamos o Spark inferir o tipo das colunas.

### [code]
%sql
select * from municipio_bd

--- out:
Databricks data profile. Run in Databricks to view.

### [code]
%sql
select m.* from municipio_bd m where m.id_municipio_rf not in (select codigo from municipio)

### [code]
%sql
select m.* from municipio m where m.codigo not in (select id_municipio_rf from municipio_bd)

### [markdown]
**Análise**:

- Temos 5570 registros na base, o que é compatível com a qtd de municípios declarada pelo IBGE (https://pt.wikipedia.org/wiki/Munic%C3%ADpios_do_Brasil#:~:text=Atualmente%20existem%205%20571%20munic%C3%ADpios,PE)%20em%20todo%20territ%C3%B3rio%20nacional.) - vale lembrar que este nr é dinâmico, dependendo da época alguns municípios podem ter surgido por ter se desmembrado de outro maior (relativamente comum) ou terem se juntado a outros para formar um maior (mais raro)
- Como se trata de uma base curada de forma cuidadosa, a maior parte dos campos está preenchida conforme esperado. Todas as linhas tem os ids preenchidos, em especial os dois que utilizaremos , `id_municipio`, `id_municipio_rf` , que representam respectivamente os ids na base do IBGE e na base da RFB. O da RFB usaremos no join com as tabelas de empresa, estabelecimento e municípios da RFB
- Os nomes dos municípios (`nome`) todos estão preenchidos, mas é importante notar que os nomes estão, ao contrário da base da RFB, acentuados. Isso não é um problema, é até melhor, usaremos esse campo de nome ao invés da RFB
- Nem todos os campos fazem sentido estarem preenchidos. Por ex, nem todos os municípios pertencem a uma região metropolitana, motivo pelo qual os respectivos campos (`id_regiao_metropolitana`, `nome_regiao_metropolitana`) viriam nulos
- Outros campos de interesse nossos (`sigla_uf`, `nome_regiao_imediata`, `nome_regiao_intermediaria`) estão todos devidamente preenchidos para todos os registros
- Não é relevante para nossa análise, mas é interessante ver que o campo georreferenciado `centroide`, que traz as coordenadas de latitude e longitude do centróide do município em questão, está sempre corretamente preenchido também, o que pode ser útil em análises georreferenciadas
- Não há municípios que existam nessa base e não existam na da RFB. Entretanto, há 2 municípios representados na base da RFB que não existem nesta base tratada do IBGE. Um dos registros na verdade traz na descrição "Exterior", i.e. não é um município. O outro município é o de 'BOA ESPERANCA DO NORTE', que aparentemente foi criado em out/23, após a base ter sido confeccionada (set/23). Então ambos os casos são pontuais e bem justificados e não devem causar problema nas análises

### - CNAEs / Base dos Dados (tabela cnae_bd)

### [markdown]
Os dados da tabela de `cnae_bd` são provenientes do portal Base dos Dados (BD) e tem descrições e metadados disponíveis em:

https://basedosdados.org/dataset/33b49786-fb5f-496f-bb7c-9811c985af8e?table=8a02c4e5-1718-41e7-8891-d0fa09265d58

Apesar de termos descritos os tipos (que são majoritariamente string/char), por simplificidade, inicialmente também deixamos o Spark inferir o tipo das colunas.

### [code]
%sql
select * from cnae_bd

--- out:
Databricks data profile. Run in Databricks to view.

### [code]
%sql
select c.* from cnae c where c.codigo not in (select subclasse from cnae_bd)

### [markdown]
**Análise**:

- Temos 1356 registros na base, o que é compatível com a qtd de CNAEs disponibilizados pelo IBGE (https://concla.ibge.gov.br/images/concla/documentacao/CNAE_Subclasses_2_3_Estrutura_Detalhada.xlsx) 
- Como se trata de uma base curada de forma cuidadosa, a maior parte dos campos está preenchida conforme esperado. Todas as linhas tem os ids preenchidos, em especial o que utilizaremos `subclasse`, que representa o código do CNAE folha na base do IBGE. 
- As descrições do CNAE (`descricao_subclasse`) estão sempre preenchidas. As descrições das agregações de CNAEs (`descricao_classe`, `descricao_grupo`, `descricao_divisao`, `descricao_secao`) também estão sempre preenchidas, mas é importante notar que como são agregadas, os valores se repetem bastante entre os registros - quanto mais agregado, menos valores distintos se tem.
- Há 3 CNAEs que existem na base da RFB e não existem nessa base. Um dos CNAEs representa o caso de CNAE não especificado. Os outros 2 CNAEs são CNAEs que não existem mais na classificação atual (CNAE 2.3). São casos pontuais e bem justificados e não devem causar problema nas análises
