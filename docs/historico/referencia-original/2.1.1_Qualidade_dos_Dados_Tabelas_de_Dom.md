# Análise da Qualidade de Dados das Bases Cruas


Na sequência, faremos uma breve análise da qualidade dos dados das bases cruas recém carregadas. Essa análise é importante para detectar (e se possível corrigir) possíveis problemas que possam afetar as análises futuras. 

OBS: esta análise foi dividida em diversos notebooks devido a uma dificuldade de exportar o notebook original porque estava muito grande.

### [markdown]

Vamos começar primeiro pelas tabelas de domínio da RFB (CNAEs, Municípios, Natureza Jurídica e Motivos de Situação). O esperado é que as tabelas estejam todas preenchidas, sem registros com campos vazios.


### [markdown]

### - CNAEs - RFB (tabela cnae)

### [markdown]
Os dados da tabela de `cnae` são provenientes da Receita Federal (RFB) e tem descrições e metadados disponíveis em:

https://www.gov.br/receitafederal/dados/cnpj-metadados.pdf

Com relação ao tipo de cada dado, como não temos mais infos, deixamos o Spark inferir o tipo de cada coluna.

### [code]
%sql
select * from cnae

--- out:
Databricks data profile. Run in Databricks to view.

### [code]
%sql
select count(*), count(distinct codigo), count(distinct descricao) from cnae

--- out:
Databricks data profile. Run in Databricks to view.

### [code]
%sql
select descricao, codigo from cnae where descricao in (select c.descricao from cnae c group by c.descricao having count(c.codigo) > 1) order by descricao, codigo

### [markdown]
**Análise**:

- Temos 1359 registros na base de CNAEs, o que é compatível com a tabela disponibilizada pelo IBGE (https://concla.ibge.gov.br/images/concla/documentacao/CNAE_Subclasses_2_3_Estrutura_Detalhada.xlsx) 
- Todos os registros na base possuem coluna `codigo` preenchida. Esta coluna é numérica e representa o id da subclasse (CNAE "folha", nível mais detalhado) de atividade econômica na classificação do IBGE. Todos os valores de `codigo` são distintos, conforme esperado - ou seja, não há 2 registros com mesmo `codigo`, o que caso existisse poderia levar a problemas de multiplicidade de registros em joins
- Com relação a `descricao`, todos os registros também tem a coluna preenchida. Por outro lado, curiosamente, há alguns poucos registros com mesmo valor de `descricao`. Aparentemente é um erro na base, seriam CNAEs "raiz", não "folha", ou que não existem mais segundo o IBGE porque foram depois abertos em vários outros mais específicos, mas a RFB manteve na lista (ex: 3511500).  Para evitar problemas, iremos trazer os dados de CNAE da base de CNAEs 2 (versões 2.x) do site Base dos Dados, que também já traz outras infos interessantes já tratadas como Classe, Grupo e Divisão  para uma visão mais agregada dos CNAEs

### - Municípios - RFB (municipios)

### [markdown]
Os dados da tabela de `municipios` são provenientes da Receita Federal (RFB) e tem descrições e metadados disponíveis em:

https://www.gov.br/receitafederal/dados/cnpj-metadados.pdf

Com relação ao tipo de cada dado, como não temos mais infos, deixamos o Spark inferir o tipo de cada coluna.

### [code]
%sql
select * from municipio

--- out:
Databricks data profile. Run in Databricks to view.

### [code]
%sql
select count(*), count(distinct codigo), count(distinct descricao) from municipio

### [code]
%sql
select descricao, codigo from municipio where descricao in (select m.descricao from municipio m group by m.descricao having count(m.codigo) > 1) order by descricao, codigo

### [markdown]
**Análise**:

- Temos 5572 registros na base de Municícipios da RFB, o que é compatível com a quantidade de municípios declarada pelo IBGE (https://pt.wikipedia.org/wiki/Munic%C3%ADpios_do_Brasil#:~:text=Atualmente%20existem%205%20571%20munic%C3%ADpios,PE)%20em%20todo%20territ%C3%B3rio%20nacional.) - vale lembrar que este nr é dinâmico, dependendo da época alguns municípios podem ter surgido por ter se desmembrado de outro maior (relativamente comum) ou terem se juntado a outros para formar um maior (mais raro)
- Todos os registros na base possuem coluna `codigo` preenchida. Esta coluna é numérica e representa o **id do município na classificação da RFB**, não na do IBGE. Todos os valores de `codigo` são distintos, conforme esperado - ou seja, não há 2 registros com mesmo `codigo`, o que caso existisse poderia levar a problemas de multiplicidade de registros em joins
- Com relação a `descricao`, todos os registros também tem a coluna preenchida. Por outro lado, há vários registros com mesmo valor de `descricao`. Aparentemente é comum termos cidades de mesmo nome em UFs diferentes - ex: o município 'AGUA BRANCA' existe em 3 UFs diferentes, Piauí, Paraíba e Alagoas, mas infelizmente não há essa info de UF na tabela disponibilizada pela RFB. Para evitar problemas, faremos o join com a base de Municípios da Base dos Dados (BD) e de lá traremos os dados de município e UF

### [code]
%sql

### [markdown]
**Análise**:

- Temos 90 registros na base de Naturezas Jurídicas da RFB, o que é compatível com a quantidade de naturezas jurídicas declarada pelo IBGE (https://concla.ibge.gov.br/estrutura/natjur-estrutura/natureza-juridica-2021) - vale lembrar que este nr é dinâmico, dependendo da época algumas novas naturezas mais especializadas podem ter surgido e outras antigas terem sido descontinuadas
- Todos os registros na base possuem coluna `codigo` preenchida. Esta coluna é numérica e representa o id da natureza jurídica. Todos os valores de `codigo` são distintos, conforme esperado - ou seja, não há 2 registros com mesmo `codigo`, o que caso existisse poderia levar a problemas de multiplicidade de registros em joins
- Com relação a `descricao`, todos os registros também tem a coluna preenchida. Por outro lado, há 2 registros com mesmo valor de `descricao`. Isso não chega a ser um problema porque são justamente os registros que indicam "Natureza Jurídica não informada" . Como esse valor não é esperado em geral de ser usado, não tomaremos nenhuma ação neste caso

- Todos os registros na base possuem as colunas `descricao` preenchida. Esta coluna traz o motivo da situação propriamente dito. Todos os valores de `descricao` são distintos, conforme esperado - ou seja, não há 2 registros com mesmo `descricao`, o que caso existisse poderia levar a problemas de multiplicidade de registros em joins
